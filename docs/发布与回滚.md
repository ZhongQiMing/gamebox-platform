# 发布与回滚

## 为什么要有版本号

镜像标签以前是 `gamebox-server:latest`。`latest` 不是版本号，就是「最新」两个字。
服务器 `docker load` 一个同样叫 `latest` 的新镜像时，Docker 会把这个标签从旧镜像上
摘下来贴到新的，**旧镜像随即变成没有名字的 `<none>`**，启动不了，下次清理就没了。

结果就是：上线后发现问题想退回上一版，服务器上已经不存在上一版了，只能回本机
重新构建、重新上传，十几分钟起步——这十几分钟里玩家一直在用出问题的版本上下分。

现在标签是 `gamebox-server:20260808-035012-442dde6`（日期-时刻-git 提交号），
每一版都有自己的名字，谁也不会覆盖谁。服务器保留最近 **3** 套，
回滚就是改 `.env.prod` 里的 `GAMEBOX_VERSION` 再重启，十几秒。

## 发一次版

### 1. 本机构建

```powershell
$env:PLAYER_ORIGIN = 'https://app.example.com'
$env:GAME_ORIGIN = 'https://games.example.com'
pnpm build:images
```

它会：构建 server 与 web 两个镜像 → 都打上同一个版本号 → 导出成
`dist-images/gamebox-images-<版本号>.tar.gz` → 生成同名 `.manifest` 完整性清单
（归档 SHA-256、两个镜像 ID、Git commit、Compose SHA-256）→ 打印出下一步的命令。

两个镜像强制同版本号。前后端分开回滚会出现「新前端调旧接口」，比不回滚还糟。

工作区有未提交改动时默认**拒绝构建**。只有紧急情况才允许显式
`-AllowDirty -DirtyReason '事故说明'`；版本标签会带 `-dirty-emergency`，原因与
`dirty=1` 会写进完整性清单和服务器发布历史，不能伪装成可复现的正式构建。

### 2. 上传

```powershell
scp dist-images/gamebox-images-<版本号>.tar.gz `
    dist-images/gamebox-images-<版本号>.manifest `
    root@<服务器>:/tmp/
scp docker-compose.prod.images.yml `
    scripts/deploy-on-server.sh `
    scripts/rollback-on-server.sh `
    scripts/backup-on-server.sh `
    scripts/restore-on-server.sh `
    scripts/check-tls-on-server.sh `
    scripts/verify-runtime-security.sh `
    scripts/health-alert.mjs `
    root@<服务器>:/tmp/
```

运维脚本必须**每次都传全**。以前这里只写了 deploy 和 rollback，
结果服务器上要么没有备份脚本，要么留着几个月前的旧版本——
需要恢复的那天才发现，是最贵的一种发现方式。

### 3. 部署

```bash
ssh root@<服务器>
PUBLIC_BASE_URL=https://app.example.com \
ADMIN_BASE_URL=https://admin.example.com \
GAME_BASE_URL=https://games.example.com \
  bash /tmp/deploy-on-server.sh
```

脚本会先核验归档 SHA-256、Compose SHA-256，并在 `docker load` 后核对两个镜像 ID；
然后依次：**停旧服务前完成 Trivy 镜像扫描** → 起数据库 → 跑迁移 → 起应用 → 健康检查
→ **强制运行时容器加固验收**
→ **强制三 Origin TLS/端口映射验收** → 写入备份与探活定时任务 → 清理旧镜像
→ 把安全/TLS结果及全部告警写入发布历史。

上传的 Compose、manifest 和运维脚本先留在隔离候选区。镜像扫描、迁移、健康、运行时和
TLS 全通过后，才原子落位 Compose、`.env.prod`、`server/.env.production` 与运维脚本；
任何预切换失败都不会覆盖当前线上文件。首装也使用候选 env 显式传入版本，不依赖 `latest`
或预先存在的 `server/.env.production`。

TLS 自检分别检查玩家、管理、游戏三个 Origin 的 HTTP→对应 HTTPS、证书 SAN/主机名与
有效期、HTTPS 200/HSTS，并把各域名的 Host+SNI 响应逐字节对照 8080/8081/8082
约定入口（详见 [`反向代理与TLS.md`](./反向代理与TLS.md)）。任何硬失败都会在宣布成功、
清理旧镜像之前触发 fail-closed 回滚。

定时任务是幂等的：已存在就不改（保留运营调过的时间）。crontab 写入失败不会在应用
已验收后造成脚本半退出，而会作为高可见告警继续收尾并写入发布历史；发布后必须手工补齐。
没配异地备份时每次部署都会提示一次，别当噪音忽略。

**新版起不来时它会自动退回上一版**，并把失败版本的最近 50 行日志打出来。
新版的镜像仍留在服务器上，修好代码重新发即可。

Origin 隔离首发改变了 web 镜像的三端口契约。没有
`org.gamebox.player-origin` / `org.gamebox.game-origin` 标签的旧镜像会被回滚脚本排除；
首发这一次不能依赖跨契约自动回滚，应先做灰度与完整探活。之后同契约版本恢复正常回滚。

## 回滚

```bash
bash /opt/gamebox-platform/rollback-on-server.sh
```

不带参数是列出可回滚的版本、各自的部署时间，以及最近几次发布记录。
选好之后：

```bash
bash /opt/gamebox-platform/rollback-on-server.sh 20260805-224500-9f8e7d6
```

切换前脚本会列出**「那一版部署之后又跑过哪些数据库迁移」**，让你先确认再输 `yes`。
原因见下一节。

---

## 回滚只回代码，不回数据库

Prisma 的迁移是单向的，**没有「退回上一版表结构」这种命令**。所以回滚之后，
旧代码会跑在新表结构上。

| 迁移类型 | 能否直接回滚 | 为什么 |
|---|---|---|
| 加可空字段 | 可以 | 旧代码看不见它，不写也不报错 |
| 加新表 | 可以 | 旧代码完全不碰 |
| 加索引 | 可以 | 只影响性能 |
| 加**必填**字段 | **不行** | 旧代码不知道要填，一插入就报错 |
| 删字段 / 改字段类型 | **不行** | 旧代码还在读写那个字段 |
| 加唯一约束 | **不行** | 旧代码可能写入重复值 |

碰到下半张表的情况，两条路：先手工把表结构改回去再回滚，或者干脆别回滚、直接
往前修一版发上去。**别在没确认的情况下硬切**——回滚变成第二次事故比第一次更难收拾。

规避办法是让迁移天然可回滚：加字段先加成可空的、跑一版；等新代码全量生效后，
下一版再补上非空约束。

## 服务器上都留了什么

在 `/opt/gamebox-platform/`：

| 文件 | 用途 |
|---|---|
| `.env.prod` | 数据库/JWT/Redis 密钥，以及当前版本号 `GAMEBOX_VERSION`。**丢了数据库就打不开了，务必单独备份** |
| `server/.env.production` | 应用的运行配置，每次部署由脚本重新生成 |
| `deploy-history.log` | 每次发布/回滚的时间、版本、上一版。回滚脚本靠它算迁移影响 |
| `docker-compose.prod.images.yml` | 服务编排 |
| `rollback-on-server.sh` | 回滚脚本，随每次部署一起更新 |
| `check-tls-on-server.sh` | 对外 TLS 自检，部署结尾自动跑，也可随时手动跑 |
| `verify-runtime-security.sh` | Trivy 最终镜像与非 root/只读/网络隔离验收 |

镜像本身在 Docker 里，用 `docker images gamebox-server` 看。

**不要跑 `docker system prune -a`**：它会把没在运行的镜像全删掉，
也就是把你所有可回滚的版本一次清空。要清理空间就让部署脚本自己清，
它只删超出 3 套的那些。

## 出问题时先看什么

```bash
cd /opt/gamebox-platform
docker compose -f docker-compose.prod.images.yml --env-file .env.prod ps        # 谁没起来
docker compose -f docker-compose.prod.images.yml --env-file .env.prod logs --tail 100 server
cat deploy-history.log                                                          # 最近发了什么
```

`web` 容器依赖 `server` 健康才会启动，所以 server 起不来时整站都打不开——
先看 server 的日志，不用怀疑 nginx。
