# 上线验收清单（App 逐游戏）

> 原则：钱与中奖只认服务端；注单核对右侧是投注合计不是赢钱；大厅无假开奖号。
>
> 这份是逐游戏玩法核对。整套系统能不能上（命令、两本账、暴露面、打包、回退）
> 见 [`上线自检清单.md`](./上线自检清单.md)。

## 运营控制台与运维（上线前）

- [ ] `pnpm check:encoding` 通过（H5 中文编码 + 内联脚本语法 + ps1 的 BOM + sh 的换行）
- [ ] `pnpm audit:rtp` 显示「硬阻断 0 项」；逐项确认低返还/毛利过薄警告，并检查末尾软控仿真没有异常回退
- [ ] `pnpm --filter @gamebox/server test` 全绿（含金额取整、赔率口径、信用盘分账、订单号校验）
- [ ] `pnpm --filter @gamebox/server test:db` 全绿（幂等、并发扣款、下分冻结、盘分额度）
- [ ] `pnpm --filter @gamebox/client-app test` 全绿（订单号格式、APK 接口地址、余额分房、本地缓存兜底）
- [ ] **隐私政策与实际做法一致**：`client-app/src/views/PrivacyPolicyView.vue` 顶部
  `OPERATOR`=澳门金御汇；联系方式走应用内客服，不留邮箱。

  保留口径已与实现对齐，页面上写的就是系统真正做的：个人信息注销即清、
  余额注销时清零、资金与游戏记录长期保留。**没有承诺任何删除期限**，
  所以不需要清理任务，也不存在「写了不做」。

- [ ] 注销余额清零已知会到位：玩家端二次确认弹窗会报出具体金额，隐私政策也写明会清零。

  余额不阻止注销（下分最低 500，拦住会让小额玩家永远注销不了），确认后残额
  **转回平台池**并记双边流水——不给代理，也不能不记账，否则每日对账的
  「流水合计 == 余额」当场就破。

  连真实 Postgres 跑，会自动建 `<库名>_test` 并迁移，**不碰开发库**（库名不以 `_test`
  结尾直接拒跑）。这批用例专测 mock 测不出来的东西：唯一约束、行锁、
  「余额 + 变动额 >= 下限」这个写在 SQL 里的守卫。改 `PointsService`、
  `writeAgentQuotaInTx`、账户下限或任何幂等键规则后必跑。
- [ ] 后台「资金对账」页点「立即对账」，四项全部通过

  自动执行为每天 05:00（上海，落在 04:00–06:00 维护窗内）。四条不变量：

  | 检查 | 含义 | 查出行说明 |
  |---|---|---|
  | 积分账 | 逐账户 `SUM(PointsLedger.amount)` == `balance` | 有代码绕开 `PointsService` 直接改余额 |
  | 盘分账 | 逐代理 `SUM(AgentQuotaLedger.delta)` == `pointsQuota` | 有代码绕开 `writeAgentQuotaInTx` |
  | 冻结额 | 玩家 `frozen` == 待审下分单合计 | 下分审核流程中断，钱卡在冻结里 |
  | 负数哨兵 | 玩家 `balance`/`frozen` 不为负 | 扣款下限保护被击穿 |

  查出差额**先查原因再修**。差额一定产生于最近 24 小时（每天对一次），
  拉该账户这段时间的流水与操作日志比对，金额本身往往就能指认是哪笔操作。
  定位后先改代码堵源头，再在页面上「补记差错调整」——只写一条 `ADJUST` 流水
  记录差额来路，**不动余额**；钱该不该退给谁是另一件事，走正常上下分。

- [ ] 探活接口 `GET /api/health/reconcile` 可访问（账对得上返 200，有差额返 503）

  只念 05:00 那次算好的缓存、不查库。**不要**接进容器探针——
  容器探针只看 `/api/health`，对账 503 触发重启只会把服务搞崩，账还是不对。

- [ ] 客服可达面未被放宽：`console.controller.cs-scope.spec.ts` 通过

  客服只该有 8 个接口（自己的额度/佣金、给派单玩家上下分、派单玩家详情、自己的流水）。
  `RolesGuard` 在方法上找不到 `@Roles` 会退到类级、类级又是兜底放行，所以
  **控制台类级默认角色里绝不能出现 CS**——否则此后每加一个接口客服都自动能读，
  而且不会有任何报错。要给客服开口子，在方法上单独写 `@Roles(..., 'CS')` 并同步改 spec 白名单。

- [ ] 镜像带版本号且服务器上留有可回退的旧版（详见 [`发布与回滚.md`](./发布与回滚.md)）

  本机 `pnpm build:images` 出包，标签形如 `20260808-035012-442dde6`；部署后
  `docker images gamebox-server` 应能看到当前版 + 前两版。**看到 `latest` 说明
  用的是老流程，出事退不回去**。回滚：`bash /opt/gamebox-platform/rollback-on-server.sh`。

  回滚只回代码不回数据库（Prisma 迁移单向）。所以迁移要写成天然可回滚的：
  加字段先加可空的发一版，下一版再补非空约束。回滚脚本会先列出「目标版本之后
  跑过哪些迁移」让你确认，别跳过这一步。

- [ ] **别在服务器上跑 `docker system prune -a`**：会把所有未运行的镜像删光，
  等于一次清空全部可回滚版本。清理交给部署脚本，它只删超出 3 套的。

- [ ] 按 [`控制台角色验收清单.md`](./控制台角色验收清单.md) 四角色手测通过
- [ ] 生产改管理员密码；seed 使用 `SEED_ADMIN_PASSWORD` 或 `SKIP_ADMIN_SEED=1`
- [ ] 宝塔每日 04:30 跑 `bash /opt/gamebox-platform/backup-on-server.sh`
  （详见 [`备份与恢复.md`](./备份与恢复.md)）

  一个包含数据库 + `.env.prod` + 上传文件。少任何一样，恢复出来都是残废系统：
  库文件在但密钥丢了照样打不开，凭证图片存在另一个 docker 卷里也不在库中。
  失败会发 Telegram（token 填 `/opt/gamebox-platform/backup.env`）。

- [ ] **上线前先做一次恢复演练**，之后每月一次：

  ```bash
  bash /opt/gamebox-platform/restore-on-server.sh --rehearse latest
  ```

  灌进临时库核对行数与余额合计，六项全「一致」才算通过，不动线上数据。
  没恢复过的备份不算备份——包损坏、导出漏表、外键顺序报错这些问题，
  只有真恢复一次才会暴露，等出事那天第一次尝试是最糟的时机。

- [ ] **每周至少下载一份备份包到本机**。默认存放的 `/opt/gamebox-backups/`
  跟数据库在同一块硬盘上，只防误删、不防硬盘坏和服务器被回收。

- [ ] 对账告警：复制一份 health-alert 定时任务，`HEALTH_URL` 指向 `/api/health/reconcile`
