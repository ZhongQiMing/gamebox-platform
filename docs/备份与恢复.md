# 备份与恢复

数据库里存着所有玩家账号、余额、每一笔上下分流水、代理额度和佣金账。
这些东西只存在服务器那一块硬盘上——硬盘坏了、服务器被回收了、或者误跑一条命令
清空了表，没有备份就全没了，玩家说「我昨天充了五千」你连查都没法查。

## 备了什么

每天打成**一个包** `gamebox-backup-<日期>-<时刻>.tar.gz.auth.enc`
（未启用加密时没有 `.auth.enc` 后缀），里面五样：

| 内容 | 为什么必须要 |
|---|---|
| `db.sql` | 数据库全量导出 |
| `env.prod` | 数据库密码和 JWT 密钥。**库文件还在但密码丢了，一样打不开** |
| `uploads.tar.gz` | 充值凭证、头像。存在另一个 docker 卷里，不在数据库中 |
| `private-uploads.tar.gz` | 客服私有媒体。与公开上传分卷保存 |
| `manifest.txt` | 备份时刻的行数、余额合计、最大的几张表。恢复后拿它逐项对照 |

打成一个包是刻意的：数据库和两个上传卷必须属于同一个一致恢复点，分开存迟早会对不上；
而且你要手动下载，一天一个文件最不容易出错。

## 每天自动备份

`deploy-on-server.sh` 会在部署时自动写入 crontab（每天 **04:30**，早于 05:00 的自动对账）：

```bash
30 4 * * * bash /opt/gamebox-platform/backup-on-server.sh >> /opt/gamebox-platform/backup.log 2>&1
```

已存在就不覆盖，改过时间的话保留你改的。**上线当天仍要 `crontab -l` 亲眼确认一次**：
写入失败只打印一行提示，不会让部署失败。没有 crontab 的机器请在宝塔计划任务里手工加。

脚本会：磁盘余量检查 → 记录 server/web 原运行状态 → **短暂停止 server/web**
→ 钻进容器 `pg_dump` → 打包密钥和两个上传卷 → 记录行数 → 恢复并验证应用健康
→ 打包 → **自检** → **加密** → 清理超过 14 天的旧包。

停止应用是为了形成一致恢复点：`pg_dump` 的数据库快照本身是一致的，但如果同时还有
上传请求写入卷，数据库可能已经引用一个尚未进入归档的文件，或归档里出现数据库没有的文件。
备份窗口内 **postgres 和 redis 不停**，只停止会写数据库/文件的 server 与 web。
脚本用 `EXIT` trap 保证成功或失败都会恢复备份前的运行状态，并等待原本运行的容器重新健康；
若恢复失败，整个任务返回失败并发出高优先级告警，绝不会把“包做出来了”当成备份成功。

`pg_dump` 是在容器里跑的。Postgres 没有对外开端口，宿主机上也没装 PostgreSQL，
在宿主机直接跑 `pg_dump` 既连不上也找不到命令。

**自检这一步很关键**：验证包能解压、四个文件齐全、dump 里表数量正常、
`User` 表确实有数据段。没有自检的话，你可能连着几个月都在生成空包而毫不知情。

任何一步失败都会发 Telegram。把 token 填在 `/opt/gamebox-platform/backup.env`：

```
TELEGRAM_BOT_TOKEN=xxx
TELEGRAM_CHAT_ID=xxx
```

变量名跟 `scripts/health-alert.env` 一样，直接抄过去即可。没配就只写日志不发消息。

## 加密

包里带着 `env.prod`，也就是数据库密码和 JWT 密钥。这个包一旦推去对象存储、
发进群里、或者存在某台谁都能登的机器上，等于把整个平台交出去了。所以默认加密：

```
BACKUP_ENCRYPT_KEY=<64 位十六进制>
BACKUP_AUTH_KEY=<另一组独立的 64 位十六进制>
```

`deploy-on-server.sh` 首次部署时自动生成并写进 `/opt/gamebox-platform/backup.env`
（`chmod 600`），之后一直复用。备份使用 AES-256-CBC + PBKDF2（20 万次迭代）
加密，并用独立随机认证密钥执行 HMAC-SHA-256 Encrypt-then-MAC，
产物仍是单文件 `.tar.gz.auth.enc`。HMAC 固定写在密文尾部，异地复制时不会漏掉认证标签。

顺序是**先自检明文包、再加密**：加密后的包没法 `tar -t`，反过来做就只能验证「解得开」，
验证不了「里面是不是一个完整的库」。加密后先验证密文 HMAC，再解密回来跑一次 `gzip -t`；
恢复脚本也严格先验 HMAC、后解密，损坏或被篡改的 CBC 密文不会进入解密器。

**两把密钥必须一起单独存到服务器之外**：

```bash
grep '^BACKUP_\(ENCRYPT\|AUTH\)_KEY=' /opt/gamebox-platform/backup.env
```

它们不会跟着备份包走（跟着走就等于没加密）。密钥和包放在同一台机器上，
服务器整台没了就全部没了——而那正是最需要备份的时候。**任一密钥丢失，包就无法验证或解密**，
没有找回的办法。同理，**不要中途换密钥**，换了之后已有的包会失效。

恢复时 `restore-on-server.sh` 从同一个 `backup.env` 读取两把密钥：
新版 `.auth.enc` 必须带有效 HMAC，缺失或损坏时不会降级解密；加密之前留下的明文老包
照样能恢复。旧版没有 HMAC 的 `.enc` 默认拒绝解密；只有先从可信离线副本核对文件后，
才可对单次命令显式设置
`ALLOW_LEGACY_UNAUTHENTICATED_BACKUP=1`，恢复完成后应立即生成新版认证备份。

## 异地副本

备份包默认放在 `/opt/gamebox-backups/`，**跟数据库在同一块硬盘上**。
这只防「误删表」，不防硬盘坏和服务器被回收。

### 自动推走（推荐）

在 `/opt/gamebox-platform/backup.env` 里配一条命令，`$1` 是刚生成的包：

```bash
# rclone（对象存储 / 网盘）
BACKUP_OFFSITE_CMD='rclone copy "$1" remote:gamebox-backups'

# 或者推到另一台机器
BACKUP_OFFSITE_CMD='scp "$1" backup@另一台:/backups/'
```

备份自检通过后自动执行；推失败会发 Telegram，本地包保留。
成功时间记在 `/opt/gamebox-backups/.last-offsite`。

### 没配的话

脚本每周一会发一条 Telegram 提醒，别当噪音。手工下载：

```bash
scp root@<服务器>:/opt/gamebox-backups/gamebox-backup-<最新那个>.tar.gz.auth.enc .
```

很多人备份做了两年，出事那天才发现备份和数据是一起没的。

## 恢复演练：每月一次

**没恢复过的备份不算备份，只算一个占地方的文件。**

备份文件损坏、导出漏表、恢复顺序触发外键报错——这些问题只有真恢复一次才会暴露。
等出事那天第一次尝试，是最糟糕的时机：那时候你在停机、玩家在等，
而你在看一条从没见过的报错。

演练是一条命令，**完全不动线上数据**：

```bash
bash /opt/gamebox-platform/restore-on-server.sh --rehearse latest
```

它把备份灌进一个临时库 `gamebox_restore_test`，然后拿 `manifest.txt` 逐项核对：

```
  项              备份时         恢复后         结果
  User             10             10             一致
  PointsAccount    12             12             一致
  PointsLedger     3243           3243           一致
  Agent            6              6              一致
  Room             3              3              一致
  balance_sum      100034690.44   100034690.44   一致
```

全部「一致」才算通过，临时库随后自动删除。有任何一项对不上，说明这个备份救不了命，
当场查原因，别等真出事。

看有哪些包可选：

```bash
bash /opt/gamebox-platform/restore-on-server.sh
```

## 真出事了怎么恢复

```bash
bash /opt/gamebox-platform/restore-on-server.sh --production gamebox-backup-20260808-043000.tar.gz.auth.enc
```

要手动输入 `RESTORE` 确认。脚本会：

1. 停掉 server 和 web（顺带断开占住数据库的连接）
2. **先把当前状态另存一份**到权限为 `0700` 的 `pre-restore-<时刻>/` 目录——
   其中含数据库和两个上传卷的安全副本，恢复错了还能退回去
3. 在覆盖前验证包内的两个上传 tar，并为当前 `uploads` / `private-uploads` 真实卷各做一份安全副本
4. 重建数据库、导入；拿 manifest 核对行数，任一项不一致立即停止，绝不启动应用
5. 还原上传文件
6. 用**当前部署镜像**执行 `prisma migrate deploy`
7. 同时等待 server 与 web（三个 HTTP 端口）健康

脚本按已创建的 `gamebox-server` 容器 Mounts 的 Destination 解析实际 Docker 卷名，
不猜 Compose project 前缀。容器停止不影响解析；如果容器从未创建、挂载不是 volume、
或实际卷已经不存在，脚本会 fail closed，不会创建同名空卷。

恢复失败时，应用保持停止，并自动尝试用 `pre-restore-<时刻>/` 中的数据库和两个卷副本
恢复操作前状态。无论自动恢复结果如何，副本都会保留，脚本会打印明确的手工恢复路径。
备份中的 `env.prod` 只用于灾难审计和找回应用密钥，**恢复脚本绝不会把其中的旧
`DB_PASSWORD` 写入已初始化的新 Postgres**。

恢复完成后必做三件事：

- 后台「资金对账」点「立即对账」，确认四项通过
- 抽查几个玩家余额，跟他们自己记的对一下
- 确认无误后再删对应的 `pre-restore-<时刻>/` 安全副本目录

**恢复会丢失备份时刻之后的所有变动。** 如果只是某张表被误改，别整库恢复——
用演练模式灌进临时库，再从临时库把那张表的数据单独捞出来。

## 换一台全新服务器

1. 装 Docker，建 `/opt/gamebox-platform`
2. 按 [`发布与回滚.md`](./发布与回滚.md) **完整部署当前版本一次**，确认 Postgres、
   server、web 都已创建并健康；保留这次生成的 `.env.prod` 和 `server/.env.production`
3. **把老服务器的 `BACKUP_ENCRYPT_KEY` 和 `BACKUP_AUTH_KEY` 都填进新机器的
   `backup.env`**——新机器部署时生成的是另外两把密钥，无法验证或解密旧包。
   这一步就是你当初被要求「单独存一份」的原因。
4. 把备份包传到 `/opt/gamebox-backups/`
5. 保持新部署的 `.env.prod` 不动，运行 `restore-on-server.sh --production <包>`。
   脚本会显示 manifest 中的备份应用版本与当前镜像版本，导入旧数据后由当前镜像补齐迁移。
6. 核对通过且 server + web 健康后，再执行资金对账和业务抽查。

**禁止删除新服务器的 `.env.prod`，也不要手工混入备份里的旧 `DB_PASSWORD`。**
Postgres 数据卷在首次部署时已用新密码初始化；把应用改成旧密码只会造成认证失败，
而恢复脚本本身也需要当前 `.env.prod` 才能连接这套基础设施。

## 备份变慢变大时看这里

`manifest.txt` 末尾记着最大的三张表。目前已知两张会无节制增长：

- `RoomChatMessage`（房间聊天，含机器人发言）
- `LotteryIssue`（每个彩种每一期）

彩票类游戏一期一两分钟，几个月就是几十万行。这两张表会让备份包越来越大、
备份越来越慢，最终撑满硬盘。它们都是「过期即无价值」的数据，
应该定期清理旧记录——这件事还没做，见待办。
